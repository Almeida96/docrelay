# Retry policy

## HTTP retries

Retry HTTP 429, 502, 503, and 504 responses. Never retry a validation error.
Honor Retry-After when present, up to the overall request deadline.
Without Retry-After, use exponential backoff with full jitter: a 200 ms base,
a 2 second cap, and at most three total attempts including the first request.
The overall deadline is 8 seconds; stop when the next delay would exceed it.

## Idempotency keys

POST /orders requires an Idempotency-Key header generated by the caller.
Keep the same key across retries of the same logical order.
The server stores the key and request-body hash for 24 hours.
Reusing the key with a different request body returns HTTP 409.
After 24 hours, reconcile the order state before trying a new key.

## Retry budgets

Retries must stay below 10% of original requests over a rolling five-minute
window. Open the circuit for 30 seconds when this budget is exhausted.
After the cooldown, allow one probe request; close the circuit only on success.
Do not stack client retries on top of worker redelivery without accounting for
the combined number of attempts.
